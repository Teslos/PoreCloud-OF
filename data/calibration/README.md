## Denominator correction: why `dict_rate` changed

The task spec said to use V_melt "at the LAST stored time" as the calibration
denominator. That is correct for Part A (an inventory snapshot) but turned out to be the
wrong physical quantity for Part C's `dict_rate = birth_rate / V_melt`, because `rate` is
meant to be a nucleation rate **per unit liquid volume that was actually present while
the pores were being born**, not per unit volume of whatever is left in the pool at the
very end of the run. Three cases made this obvious: their pools had almost fully
resolidified by the last stored time (down to 52–221 liquid cells vs. ~26,000–33,000 for
a normal pool at the same instant), so dividing by that collapsed V_melt inflated
`dict_rate` by 40–1000× and pushed the reported void fraction past 100% — the exact
"rate way too high, silently" failure mode described in the task background.

**Fix applied**, per instruction:
1. For each case with PoreTracker data, take the gas-pore (`IsKeyhole==0`) birth window
   `[t_first_birth, t_last_birth]` from `*_pores_summary.csv`.
2. Sample V_melt (same `alpha.metal>0.5 & epsilon1>0.5` cell-count method as Part A) at
   10 evenly spaced target times across that window, snapped to the nearest available
   stored time directory, de-duplicated (so a window finer than the storage interval
   doesn't overweight one frame). `n_V_melt_window_samples` records how many *distinct*
   stored times ended up being used (always ≤10; it was 10 for every case here).
3. `dict_rate = birth_rate / mean(V_melt over those samples)`. This mean is
   `V_melt_mean_window_m3` in the output.
4. As a cross-check, V_melt was also evaluated at the single stored time nearest the
   *median* birth time (`V_melt_at_median_birth_m3`). Where this differs from the window
   mean by more than 2×, `window_vs_median_ratio_gt2x = True` — a signal that the pool is
   changing size fast enough within the birth window that a single scalar rate is a weak
   description of that case (see below; this is a real limitation, not something the
   averaging "fixes").

The old last-time-based numbers are preserved as `dict_rate_lasttime_DEPRECATED` and
`V_melt_lasttime_m3_DEPRECATED` in `calibration.csv`/`calibration_full.csv` so the
difference stays visible rather than disappearing.

Net effect on the ordinary (non-collapsing) cases: `dict_rate` roughly **doubled**
relative to the deprecated last-time number (e.g. azimuthal-0.2T: 5.53e15 → 1.19e16).
This is because none of these 1ms runs reach a steady-state pool size — the melt pool is
still growing throughout the whole simulated window (see the `openfoam_projects/results/
rmf-xz-0.2T` trace below), so its time-average over the birth window is necessarily
smaller than its value at the final time. That is expected and not a red flag by itself
— see the void-fraction discussion below for where it *does* create a new problem.

### Worked example, end to end: `results/azimuthal-0.2T`

1. Mesh: 60×96×48 = 276,480 cells; domain 1.75e-10 m³; avg cell volume 6.3296e-16 m³.
2. Part A, V_melt at the last stored time (t=0.001s): 26,876 liquid cells ×
   6.3296e-16 = **1.70114e-11 m³** — matches the reference value (1.701e-11 m³, 26876
   cells, 6.33e-16 m³/cell) exactly. This is `V_melt_m3` in `inventory.csv` and
   `V_melt_lasttime_m3_DEPRECATED` in the calibration files.
3. PoreTracker summary: 79 gas pores (`IsKeyhole==0`) out of 80 rows, birth times
   1.5e-4 s to 9.9e-4 s → span 8.4e-4 s → birth_rate = 79/8.4e-4 = **94,047.6/s**.
4. **Corrected denominator**: sample V_melt at 10 times evenly spaced across
   [1.5e-4, 9.9e-4] s (snapped to the nearest of the 101 stored steps): the pool is
   still filling in over this window, so these 10 samples average to
   `V_melt_mean_window = 7.928e-12 m³` — noticeably below the final-time value of
   1.701e-11 m³, because most of the window is earlier than the fully-grown pool.
5. `dict_rate = 94,047.6 / 7.928e-12 = 1.1863e16 1/(m³·s)` (vs. the deprecated
   last-time value of 5.5285e15 — roughly 2.1× higher).
6. Cross-check: V_melt at the median birth time (≈5.2e-4 s) is 9.924e-12 m³, within 2×
   of the window mean (ratio 1.25×) → `window_vs_median_ratio_gt2x = False`, i.e. this
   case's pool growth is smooth enough that a single scalar rate is a reasonable
   description.
7. Diameters (unaffected by the denominator change, still from `MeanVolume_m3`):
   p50 = 11.11 µm, volume-weighted mean = 53.2 µm.
8. Void fraction, recomputed with the same corrected denominator: per-timestep gas-pore
   volume ÷ `V_melt_mean_window` (7.928e-12 m³) → **max = 2.20%** (up from 1.03% under
   the deprecated denominator, for the same reason as step 5 — smaller denominator).

All 35 cases share the **identical mesh**: `hex (0 1 2 3 4 5 6 7) (60 96 48)`,
domain 500×700×500 µm (vertices span exactly that box in every `blockMeshDict`

- total cells = 60×96×48 = 276,480
- domain volume = 500e-6 × 700e-6 × 500e-6 = 1.75e-10 m³
- **average cell volume = 1.75e-10 / 276,480 = 6.3296e-16 m³**

Note the mesh uses `simpleGrading` (fine near the laser track, coarser at the domain

which is a reasonable approximation when the liquid pool spans both fine and coarse
region cells, but it will systematically mis-estimate V_melt for pools that sit
disproportionately in the fine (or coarse) part of the grading. I did not have a per-cell
volume field to check this against; flagging it as a known approximation, not a bug.

### Two more cases cross the ~10% void-fraction line under the new denominator — reporting as unresolved, not rationalized away

Scanning all 26 corrected rows, two cases I had **not** originally flagged now show void
fraction above (or right at) 10%:

| case | void fraction (new) | window_vs_median ratio flag |
|---|---|---|
| `openfoam_projects/results/rmf-xz-0.2T` | **13.79%** | False |
| `openfoam_projects/results_spot/rmf-xy-0.2T` | **10.11%** | False |

Per your instruction, I am not rationalizing these away. Here is what I found tracing
both:

- Neither case's pool is collapsing — the opposite. V_melt grows **monotonically** for
  the entire 1ms run (e.g. `rmf-xz-0.2T`: 3.80e-12 m³ at t=0.2ms → 7.75e-12 at 0.5ms →
  1.68e-11 at 0.9ms → 1.98e-11 at t=0.001 (the last stored time). Neither pool reaches a
  steady size within the simulated window.
- Both cases' `max_void_fraction` occurs exactly at the last stored time (t=0.001s), and
  in both there is a real, sharp late jump in tracked gas-pore volume right at the last
  1-2 stored steps (`rmf-xz-0.2T`: summed pore volume goes 5.61e-13 → 1.194e-12 m³ from
  t=0.00099 to t=0.001, essentially doubling in the final step).
- The window-averaged denominator (8.66e-12 m³ for `rmf-xz-0.2T`, 9.20e-12 m³ for
  `results_spot/rmf-xy-0.2T`) is, by construction, an average over a still-growing pool,
  so it sits well **below** the actual instantaneous V_melt at the final time (1.98e-11
  and 1.98e-11 m³ respectively — over 2× the window mean). Dividing the late-time pore
  volume spike by the (smaller) window average instead of the actual (larger)
  instantaneous V_melt at that same moment inflates the reported ratio: recomputing
  void fraction at t=0.001 with the *instantaneous* V_melt instead of the window average
  gives 6.03% for `rmf-xz-0.2T` and 4.70% for `results_spot/rmf-xy-0.2T` — both
  comfortably under 10% (and these numbers match the deprecated last-time-based pass,
  which is expected: at exactly the last time, the "last-time" and "instantaneous"
  denominators are the same quantity).

**My diagnosis: this is a numerator/denominator time-mismatch artifact of applying one
fixed, window-averaged V_melt to a void-fraction time series whose true denominator
(the instantaneous pool size) is still rising throughout the run.** It is a different
mechanism from the original 3 cases (which had a real late-run pool collapse) — here the
pool never shrinks, it just hasn't finished growing by the time the run ends, and a
scalar time-average necessarily undershoots the true value at the far (late) edge of the
window it was computed over. I have not corrected for this because the task specified
"time-averaged V_melt over the [birth] window" as the fix, and that is what produces this
result; a further correction (e.g., using instantaneous V_melt for the void-fraction
series while keeping the window average only for `dict_rate`) was not asked for and I
did not apply it unasked. **Flagging both rows as unresolved under the specified
methodology, not silently treating them as fine.**

`openfoam_projects/results_spot/rmf-xz-0.1T` (truncated run, see Part A) also has a
comparatively small `V_melt_mean_window` (2.56e-12 m³, since the run only reached
t=0.00023s and the pool was still very immature) and a resulting void fraction of 9.23%
— under the 10% line but close to it and low-confidence given the truncated run and only
9 gas-pore births.

### Detection floor in the diameter distribution (unaffected by the denominator fix)

Diameters come from `MeanVolume_m3` in the per-pore summary and do not depend on V_melt,
so this section is unchanged from the first pass. As warned in the task, PoreTracker
cannot resolve pores below roughly the size of a few mesh cells, producing a pile-up at
a minimum diameter. Across all 26 cases the floor sits at **d ≈ 7.2–9.3 µm** (consistent
with the mesh's finest cell edge lengths of ~6.25–9.4 µm quoted in `blockMeshDict`'s
grading comments — i.e. the floor is roughly a single fine cell's linear dimension, not
literally 5 cells' worth of volume; I did not have a per-cell-size field to pin this down
more precisely than "order of mesh resolution", so treat that reconciliation as
approximate).

In most cases **p1, p5, p10 are all within ~5% of the single minimum diameter observed**
(i.e. they're the same floor value, not independent percentile estimates), and in about
half the cases **p25 is too**. p50 (median) is typically 11–19 µm — close enough to the
floor (within ~20–70%) that I would treat the median with caution as well. **Only p75,
p90, p99, and the volume-weighted mean diameter are clearly above the floor and safe to
use as physical pore-size information**; p90/p99 range roughly 15–80 µm across cases
and the volume-weighted mean (dominated by the rare large pores) ranges roughly
22–80 µm. Per-case floor diagnostics (`d_min_um`, `floor_pore_fraction`, and which
percentiles sit at the floor) are in `calibration_full.csv`.

Practical implication for `sizeDistribution`: fit/sample the *upper* part of the
measured distribution (above p50, ideally above p75) rather than the raw p1–p50 range,
since the low end is an artifact of grid resolution, not physics.

## MHD vs. no-mhd classification — an inconsistency worth flagging

Classification in `inventory.csv` (`is_nomhd_by_name`) is by directory name
(`no-mhd`/`nomhd` substring), which is reliable for grouping. But the `MHD.active`/`B0`
values **currently stored** in `constant/transportProperties` disagree with the
directory name for 3 of the 4 no-mhd controls:

| case | MHD.active (on disk now) | B0 (on disk now) |
|---|---|---|
| `openfoam_projects/results/no-mhd` | `true` | 0.1 T |
| `openfoam_projects/results_spot/no-mhd` | `true` | 0.1 T |
| `openfoam_projects/results_weld_s5e6/no-mhd` | `true` | 0.2 T |
| `results_matched_0.2T_f4000hz/no-mhd` | `false` | 0 T |

Only the last one is self-consistent with its name. For the other three I checked the
actual `LorentzForce` and `J_MHD` fields at the latest stored time rather than trusting
the dict — **this field-data check, not the on-disk dict, is what I'd trust, and I'm
recording that explicitly here per your note:**

- `openfoam_projects/results/no-mhd`: `LorentzForce` is `uniform (0 0 0)` everywhere
  (zero), but `J_MHD` is *non-uniform and non-zero* (max ~1.35e8 A/m², mean
  ~1.7e6 A/m²). This is only possible if `J = σ(U×B − S∇T)` was evaluated with **B = 0**
  (so the `U×B` term vanishes and only the Seebeck/Thomson term `−σS∇T` survives, giving
  a non-zero J but a zero `J×B` Lorentz force). In other words, the field data itself
  shows this run actually had no magnetic field, regardless of what `B0` says in the
  file today.
- `openfoam_projects/results_spot/no-mhd` and `openfoam_projects/results_weld_s5e6/no-mhd`:
  both `LorentzForce` and `J_MHD` are uniform zero — fully consistent with no MHD
  activity having occurred.

**Conclusion: the field data confirms all three behaved as genuine no-mhd controls at
runtime** (zero Lorentz body force), so I did *not* exclude them from the calibration
table. But **the on-disk `constant/transportProperties` for these three directories
should not be trusted as a record of what was actually run** — it was most likely
edited or reused as a template after the run completed. If this dict is ever used
programmatically (e.g., to auto-tag "MHD on/off" for a paper figure), it will give the
wrong answer for these 3 cases; classify by field evidence, not by the dict, or by
directory name as I did here.
